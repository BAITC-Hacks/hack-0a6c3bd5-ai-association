# Контракт API «Контур» — v1

Согласованная форма обмена для backend Данияла и frontend Мовсара. Реализуем по H1 → H2 → H3; изменение обязательного поля сначала согласуем в Git.
Все маршруты имеют префикс `/api`; версия контракта — `v1`, отдельный префикс версии в прототипе не нужен. Ответы — JSON UTF-8, имена полей — `snake_case`, тексты для пользователя — на русском.
`DEMO_MODE=1` по умолчанию: SQLite + fixtures, без внешней сети и ключей. H1 вообще не вызывает LLM. Live-режим сохраняет этот же контракт.
Примеры ниже иллюстрируют формат: цена, время снимка и идентификаторы склада условные; в сид переносим проверенные исходные данные, а не цифры из документа.

## Общие типы и правила

- `Product.id` и все `product_id` — положительные целые внутренние ID SQLite. `sku` — строка артикула каталога: не преобразовывать её в число и не терять ведущие нули. ID склада, предложения и сессии — строки.
- `price_kzt` — целое число тенге ≥ 0 либо `null`, если цена неизвестна. Для демо выбираем позиции с целыми ценами; дробную цену живого каталога молча не округляем, помечаем неподдерживаемой до расширения контракта.
- Все `quantity` — целые числа ≥ 0 либо `null` для неизвестного остатка. Демо поддерживает только целые штуки (`шт`) и целые метры (`м`); дробные количества отклоняем с 422, не округляем.
- `total_quantity` — общий остаток по данным источника; `available_quantity` — остаток только выбранного `warehouse_id`. `null` означает «нет данных», `0` — подтверждённое отсутствие. Не подставлять общий остаток вместо локального.
- `min_order_quantity` — положительное целое число либо `null`, если условие неизвестно. Для подтверждаемого демо-набора условие должно быть задано; неизвестное не считать единицей.
- В API время — ISO 8601 UTC, например `2026-09-23T07:00:00Z`; UI показывает дату `23.09.2026`, деньги `32 500 ₸`.
- `snapshot.source` — `ekt_catalog` или `demo_fixture`, `snapshot.captured_at` — реальное время сохранения данных, `snapshot.source_url` — известная ссылка источника либо `null`. Загрузка страницы не обновляет время снимка.
- `name`, `description`, `properties` сохраняются отдельно. В `properties` остаются исходные название, значение и поле источника; конфликт «160 А в описании / 250 А в свойстве» нельзя затирать одним «нормализованным» значением.
- `image_url` — локальный путь `/assets/...` либо `null`; `documents` — массив `{title, url, kind}`, `kind` = `certificate` или `datasheet`. В offline-наборе ссылки локальные; неизвестный сертификат — пустой массив.

## H1 — каталог из SQLite, без агента

`GET /api/health` → 200; недоступная или неинициализированная БД → 503 в общем формате ошибок.

```json
{"status":"ok","api_version":"v1","demo_mode":true,"database":"ok"}
```

`GET /api/warehouses` → 200. Порядок стабилен, ID внутренние; название склада сохраняем как в источнике, город показываем отдельно.

```json
{"items":[{"id":"astana","name":"Нур-Султан","city":"Астана"}],"default_warehouse_id":"astana"}
```

`GET /api/products?warehouse_id=astana&q=200300285_&limit=20&offset=0` → 200.
`warehouse_id` обязателен; неизвестный → 404 `WAREHOUSE_NOT_FOUND`. `q` необязателен (пустой = каталог), максимум 200 символов; ищем по артикулу и названию без учёта регистра. Точное совпадение артикула выше частичных; далее стабильная сортировка по `sku`, `id`.
`limit` по умолчанию 20, диапазон 1–100; `offset` по умолчанию 0, ≥ 0. `total` — число всех совпадений до пагинации; отсутствие совпадений → 200 с `items: []`.

```json
{
  "items": [{
    "id": 515291, "sku": "200300285_",
    "name": "Автоматический выключатель 160 А",
    "description": "Номинальный ток: 160 А.",
    "price_kzt": 32500, "unit": "шт", "min_order_quantity": 1,
    "warehouse_id": "astana", "available_quantity": 8, "total_quantity": 23,
    "properties": [{"name": "Номинальный ток", "value": "250 А", "source_field": "properties.Номинальный ток"}],
    "image_url": null, "documents": [],
    "snapshot": {"source": "ekt_catalog", "captured_at": "2026-09-23T07:00:00Z", "source_url": null}
  }],
  "total": 1, "limit": 20, "offset": 0, "warehouse_id": "astana"
}
```

`GET /api/products/{id}?warehouse_id=astana` → 200 с объектом `Product` без обёртки. `id` — целое > 0, неверный формат → 422 `VALIDATION_ERROR`. Объект совпадает по форме с элементом `items` списка; отсутствующий товар → 404 `PRODUCT_NOT_FOUND`. Пример для `/api/products/515291?warehouse_id=astana`:

```json
{
  "id": 515291, "sku": "200300285_",
  "name": "Автоматический выключатель 160 А",
  "description": "Номинальный ток: 160 А.",
  "price_kzt": 32500, "unit": "шт", "min_order_quantity": 1,
  "warehouse_id": "astana", "available_quantity": 8, "total_quantity": 23,
  "properties": [{"name": "Номинальный ток", "value": "250 А", "source_field": "properties.Номинальный ток"}],
  "image_url": null, "documents": [],
  "snapshot": {"source": "ekt_catalog", "captured_at": "2026-09-23T07:00:00Z", "source_url": null}
}
```

## H2 — сессия, консультант, подтверждаемая корзина

`POST /api/session`, тело `{}` → 200 `{"ready":true}`. Создаёт анонимную сессию или сохраняет существующую; не очищает корзину. Никаких пользователей, входа и регистрации.
Сервер ставит `kontur_session=<случайное непрозрачное значение>; HttpOnly; SameSite=Lax; Path=/`, `Secure` при HTTPS. Идентификатор не возвращаем в JSON и не кладём в URL. Frontend отправляет cookie; dev-сервер проксирует `/api`, публикация работает на одном origin.
H2/H3 требуют эту cookie; без сессии → 401 `SESSION_REQUIRED`. Сессия, предложения, корзина и результаты повторных запросов хранятся в SQLite. Изменяющие запросы проверяют origin; CORS не открываем для произвольных сайтов.

`GET /api/cart` → 200. `/cart` — страница текущей локальной корзины; ссылка открывается с той же сессией и не раскрывает чужую корзину.

```json
{"id":"c_1","version":0,"warehouse_id":null,"items":[],"total_kzt":0,"cart_url":"/cart","scope":"local_demo"}
```

Непустой `Cart.items`: `{product_id, sku, name, unit, quantity, unit_price_kzt, line_total_kzt}`. Суммы вычисляет сервер из SQLite; `total_kzt` = сумма строк. В корзине один склад. Цена — последняя подтверждённая; корзина не резервирует товар и не оформляет заказ. `version` увеличивается один раз при фактическом изменении.
У ekt.kz нет предоставленного контракта записи корзины: `scope: "local_demo"` честно означает корзину прототипа и сохраняется даже в live-режиме LLM.

`POST /api/chat` → 200. Тело: `message` 1–4000 символов, UUID `request_id`, существующий `warehouse_id`.

```json
{"message":"Подбери 2 штуки на 160 А","request_id":"c7b35283-07da-4e2d-9912-4b8aa9f67a47","warehouse_id":"astana"}
```

Ответ всегда содержит `message`, `products` (массив `Product`), `checks`, `proposal` (объект либо `null`), `cart`, `answer_source` (`fixture`, `rules`, `openai`), `confirmation_required` (boolean).
`checks`: массив `{product_id, field, expected, actual, status, sources}`. `status` = `match | conflict | unknown`; `expected`, `actual` — строки либо `null`; `sources` — массив `{field, value}`. Числа, остатки и проверки берём из данных/правил; LLM формулирует ответ через `app/llm.py`.
Неразрешённый конфликт существенной характеристики, неизвестная цена, минимум или локальный остаток блокируют предложение покупки позиции; ответ объясняет причину и предлагает уточнение/проверенный аналог. Нехватка на складе не компенсируется общим остатком.

`Proposal` (ниже товар с ID `1001` — условный пример уже проверенной позиции):

```json
{
  "id":"p_1","status":"pending","warehouse_id":"astana","cart_version":0,
  "items":[{"product_id":1001,"target_quantity":2,"unit_price_kzt":32500}],
  "result_total_kzt":65000,"expires_at":"2026-09-23T07:15:00Z"
}
```

`items` — изменения конкретных строк; неупомянутые строки сохраняются. `target_quantity` — итоговое желаемое количество в корзине, не добавка; 0 удаляет строку. Положительное количество соблюдает минимум и локальный остаток. `result_total_kzt` — итог всей корзины после применения предложения.
На сессию одно активное предложение; новое делает старое `superseded`. Другие статусы: `pending`, `confirmed`, `expired`. TTL — 15 минут. Склад предложения должен совпадать со складом непустой корзины, иначе 409 `CART_WAREHOUSE_CONFLICT`; смена склада требует сначала подтверждённого удаления текущих строк.

`POST /api/proposals/p_1/confirm` — отдельная кнопка «Подтверждаю добавление» (для удаления — «Подтверждаю удаление»). Тело:

```json
{"request_id":"21b0bfa8-9c2f-4311-9338-f5c98c5ff22d"}
```

Успех → 200 `{"proposal_id":"p_1","status":"confirmed","cart":{...}}`, где `cart` — полный `Cart`. Только сервер применяет сохранённое предложение текущей сессии; клиент не присылает цену, количество или признак «LLM разрешил».
В одной транзакции проверяем принадлежность, срок, статус, версию корзины, склад, актуальные цену/минимум/остаток и блокирующие противоречия. При неизменных данных применяем все строки атомарно. В demo «актуальные» означает текущую SQLite; это не обещание свежести внешнего магазина.
Цена, минимум или достаточность остатка изменились → 409 `PROPOSAL_CHANGED`, без изменения корзины; `error.details.proposal` содержит новое предложение либо `null`, если предложить покупку нельзя. Сообщение перечисляет изменения; новое предложение требует нового подтверждения.
Версия корзины изменилась → 409 `CART_CHANGED`; просим заново построить предложение. Истёкшее/заменённое → 409 `PROPOSAL_EXPIRED` / `PROPOSAL_SUPERSEDED`. Чужое предложение → 404 `PROPOSAL_NOT_FOUND`.
Текстовое «да, добавь» допускается только для единственного активного предложения этой сессии, показанного в последнем ответе. Сервер распознаёт ограниченный список однозначных фраз и запускает тот же механизм подтверждения. Смена склада/новый запрос/неоднозначный текст требуют нового предложения или уточнения; решение LLM не является авторизацией.
Повтор одного `request_id` в той же сессии и операции с тем же телом возвращает сохранённый HTTP-статус и ответ, без новых вызовов LLM и мутаций. Другое тело с тем же ключом → 409 `IDEMPOTENCY_CONFLICT`. Повтор подтверждённого `proposal_id` с новым ключом также не меняет корзину повторно и возвращает 200 с текущим `Cart`.

## H3 — короткая спецификация из файла

Отдельно от JSON-чата: `POST /api/uploads`, `multipart/form-data`: `file`, UUID `request_id`, `warehouse_id`. Максимальный размер файла 10 MiB; только `.xlsx`, `.docx`, текстовый `.pdf`, `.jpg`/`.jpeg`, с проверкой содержимого. Старые `.xls`/`.doc` и скан-PDF не поддерживаем; расширение не доказывает тип.
Успех → 200 `{"upload_id":"u_1","lines":[{"line_id":"1","query":"Автомат 160 А","quantity":2,"unit":"шт"}],"warnings":[]}`. Неуверенные `quantity`/`unit` — `null`, предупреждение объясняет сомнение. Максимум 50 строк и 10 страниц PDF; превышение → 422 `DOCUMENT_LIMIT_EXCEEDED`.
`.xlsx`/`.docx`/текстовый PDF разбираем локально; JPEG в live — через `app/llm.py`, в demo — записанный результат известного файла по хэшу. Для произвольного JPEG без доступного распознавания возвращаем 422 `OCR_UNAVAILABLE` с предложением вставить текст; не придумываем строки.
`POST /api/uploads/u_1/proposal`, JSON `{request_id, warehouse_id, lines}`: пользователь проверяет и правит распознанные строки; каждая строка имеет `line_id`, непустой `query`, целую положительную `quantity`, `unit`. Ответ той же формы, что `/api/chat`; неоднозначные позиции требуют уточнения. Загрузка и сопоставление не меняют корзину; изменение только через подтверждение предложения H2.
Файл и результаты принадлежат сессии; чужой/отсутствующий → 404 `UPLOAD_NOT_FOUND`. `request_id` действует по правилам H2, для файла сравниваем хэш и остальные поля. В исходный Git и ответы не попадают пути временных файлов.

## Единый формат ошибок

Для всех API-ошибок, включая валидацию FastAPI и непредвиденные исключения:

```json
{"error":{"code":"WAREHOUSE_NOT_FOUND","message":"Склад не найден. Выберите склад из списка.","details":{"warehouse_id":"unknown"}}}
```

`code` стабилен для кода клиента, `message` на русском для UI, `details` — объект (по умолчанию `{}`). Не возвращать traceback, ключи API и содержимое cookie.

| HTTP | Коды и назначение |
| --- | --- |
| 401 | `SESSION_REQUIRED` — сначала создать сессию |
| 403 | `ORIGIN_NOT_ALLOWED` — недопустимый источник изменяющего запроса |
| 404 | `PRODUCT_NOT_FOUND`, `WAREHOUSE_NOT_FOUND`, `PROPOSAL_NOT_FOUND`, `UPLOAD_NOT_FOUND` |
| 409 | `PROPOSAL_CHANGED`, `PROPOSAL_EXPIRED`, `PROPOSAL_SUPERSEDED`, `CART_CHANGED`, `CART_WAREHOUSE_CONFLICT`, `IDEMPOTENCY_CONFLICT` |
| 413 | `FILE_TOO_LARGE` |
| 415 | `UNSUPPORTED_FILE_TYPE` |
| 422 | `VALIDATION_ERROR`, `DOCUMENT_LIMIT_EXCEEDED`, `DOCUMENT_PARSE_FAILED`, `OCR_UNAVAILABLE` |
| 500 | `INTERNAL_ERROR` — безопасное сообщение и подробность только в серверном логе |
| 503 | `DATABASE_UNAVAILABLE` |

Для 422 `VALIDATION_ERROR`: `details.fields` — массив `{field, message}` с русским объяснением, например `{"field":"quantity","message":"Укажите целое количество."}`. Ошибка OpenAI сама по себе не приводит к 500/503: отвечаем из fixtures или правилами.

## Приёмка общего контракта

H1: после seed и запуска `health` = 200; поиск/карточка совпадают; `8` локально и `23` всего различимы; `null` и `0` отображаются по-разному; неизвестные ID и невалидные параметры возвращают общий формат ошибок.
H2: без подтверждения корзина не меняется; двойной клик не удваивает количество; изменившаяся цена требует согласия; конфликт характеристик не исчезает; две cookie-сессии не видят чужие предложения и корзины; offline-сценарий проходит без ключей.
H3: файл даёт редактируемые строки и предложение, не молчаливое добавление; неподдерживаемый файл и ошибка распознавания объяснимы пользователю.
