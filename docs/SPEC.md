# Контур — спецификация прототипа

Статус: согласованный в чате продуктовый сценарий; реализация начинается с H1. Этот документ описывает план, а не уже готовые функции.

## Пользователь и результат

Покупатель или закупщик электротоваров ekt.kz описывает потребность либо загружает спецификацию. Ассистент находит товар, показывает характеристики, сертификаты и наличие на выбранном складе, объясняет аналоги и после явного подтверждения собирает корзину.

Отличие: проверяемое сопоставление требования и данных каталога. Несогласованные характеристики выделяются как противоречие; неизвестное значение не считается подтверждённым. Ассистент не выдаёт такую позицию за проверенный аналог.

Источник требований: [официальный кейс ekt.kz](https://docs.google.com/document/d/172eSfQ4f3D2wgtsfrs8Lonr1SIwAXLx7jZ7hNccISNk/edit). API и формат ответов: [API-CONTRACT.md](API-CONTRACT.md).

## Обязательный сценарий

1. Покупатель задаёт вопрос по артикулу: ответ содержит цену, наличие, характеристики и сертификат, если он предоставлен каталогом.
2. Указывает склад и количество: интерфейс различает общий остаток и остаток на выбранном складе.
3. Если товара нет, получает релевантный аналог с обоснованием; если данных для уверенного подбора недостаточно, получает понятное уточнение.
4. Уточняет оплату, доставку и минимальную партию: ответ опирается на подтверждённые условия, а не на догадки модели.
5. Видит конкретное предложение и подтверждает его: только тогда сервер меняет корзину, повторно проверив цену, количество и доступность.
6. Открывает прямую ссылку `/cart` и видит актуальные позиции и сумму в тенге.

Реальное API изменения корзины ekt.kz пока не предоставлено. В прототипе корзина локальная; это явно указывается в UI и README. Покупка, оплата и резервирование товара в ekt.kz не выполняются.

## Экраны

- `/`: единая рабочая область с чатом, поиском, выбранным складом, карточкой товара/сравнением и компактной корзиной. В H1 работают поиск и карточка; функции следующих этапов не изображаются готовыми кнопками.
- `/cart`: актуальная корзина текущей анонимной сессии и итоговая стоимость.
- «Почему этот товар»: раскрываемая панель внутри первого экрана; требования, подтверждающие значения, источник, расхождения и недостающие сведения.

Визуальная основа: собственные React-компоненты, Tailwind и CSS; без готовой темы Material, Ant Design или shadcn. Сторонние экраны используются как референсы, а код или платные assets — только с подходящей лицензией. Все используемые шрифты и assets локальны.

## Данные и вычисления

- SQLite: товары, склады, остатки, характеристики с источниками, ссылки на сертификаты, условия покупки; с H2 — сессии, сообщения, предложения, позиции корзины и события подтверждения.
- Нормализованное поле не должно уничтожать исходные противоречащие значения. Для примера API `515291` название/описание указывали 160 А, а свойство — 250 А; это наблюдение при подготовке, не гарантия неизменности каталога.
- Для стабильного offline-демо — репрезентативный сид с указанным происхождением данных. Демонстрационные значения и условия помечаются; реальные остатки не обещаются по старому снимку.
- Деньги, доступность, ограничения количества и подтверждение проверяются кодом. LLM разбирает запросы и формулирует ответы по переданным фактам.
- DEMO_MODE=1 по умолчанию: сеть и ключи не требуются. Для записанных сценариев используются fixtures; для остальных поддерживаемых запросов — детерминированный fallback.
- DEMO_MODE=0: OpenAI через `app/llm.py`, structured outputs, timeout, retry, кэш, fallback. Сбой модели не меняет корзину и не роняет приложение.

## Этапы и ответственность

| Этап | Даниял — A, Windows 11 | Мовсар — B, macOS | Проверяемый результат |
|---|---|---|---|
| H1, до 14:00 | SQLite, seed, CLI, API каталога и складов, отдача web/dist | Vite/React/TS, поиск и карточка на API, состояния загрузки/ошибки | Поиск и выбор товара проходят в браузере на реальных данных SQLite |
| H2, до 15:00 | Сессии, чат, аналоги, условия покупки, предложения и подтверждение корзины | Чат, сравнение, подтверждение, актуальная корзина | Все пять must-have официального кейса проходят целиком |
| H3, до 16:00 | Выявление конфликтов, извлечение строк из файлов | Паспорт подбора, загрузка и исправление распознанных строк, mobile | Полный 90-секундный сценарий |
| H4, до 17:00 | Offline/live проверки, негативные сценарии, чистый клон Windows | README, схема, CREDITS, скриншоты, чистый клон macOS | Чужой человек запускает без ключей по README |
| H5, до 18:00 | Только исправление блокеров, проверка финального клона | Три репетиции, видео, питч, сдача на платформе | Финальный push до 17:50, проверка сдачи до 17:55 |

Каждый час A отправляет проверенный результат к :50, B — интегрированную часть и запись PROGRESS.md к :55. Промежуточные коммиты допускаются чаще. Общие изменения API сначала согласуются через контракт; чужие файлы не редактируются.

## Ограничения объёма

H3: короткие XLSX/DOCX, PDF с текстовым слоем, читаемые JPEG. Распознанные данные показываются для исправления человеком. Старые бинарные XLS/DOC и универсальное OCR многостраничных сканов не обещаются. Точные ограничения загрузки описаны в контракте.

Не входят: платежи, регистрация, production-интеграция корзины без предоставленного контракта, автоматическое проектирование электросетей, обучение моделей, управление ценами магазина, прогноз 30-дневной выручки, микросервисы.

Стоимость корзины не называется прибылью. Экономия считается только против конкретного сопоставимого предложения; все неизвестные данные остаются неизвестными.

## Приёмка

Выполнить `uv run hack seed`, затем `uv run hack serve`; проверить endpoint через curl и сценарий через Playwright. Проверить пустой поиск, ошибку API, нулевой/неизвестный остаток, количество сверх наличия, повторное подтверждение, отсутствие ключа и потерю сети. Сборка web/dist коммитится. Статус этапа отмечается завершённым только после интеграции; отдельно готовый фронтенд не считается работающим H1.
